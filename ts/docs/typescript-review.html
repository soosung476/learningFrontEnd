      00

      TypeScript가 실제로 하는 일

      JavaScript는 런타임에 타입이 결정됩니다. 그래서 잘못된 인자를 넘겨도 실행하기 전까지는 아무도 모릅니다. TypeScript는 그 판정을 실행 전(컴파일 시점)으로 끌어옵니다. function.ts의 예제가 정확히 그 얘기입니다.

      function.ts — 인자 개수와 타입이 코드를 쓰는 순간 검증된다
      function add(num1: number, num2: number): void {
  console.log(num1 + num2);
}

add(1, 2);              // OK
// add();               // 에러: 인자 2개가 필요함
// add(1);              // 에러: 인자가 모자람
// add(1, 2, 3);        // 에러: 인자가 많음
// add("Hello", "World") // 에러: string은 number에 대입 불가

      컴파일 흐름 — 타입은 실행되지 않는다

      가장 중요한 한 줄입니다. 타입 표기는 컴파일 후 전부 지워집니다(type erasure). tsc가 src/*.ts를 읽어 dist/*.js를 만들고, 브라우저·Node가 실행하는 건 그 .js뿐입니다. 그래서 타입은 런타임 동작을 절대 바꾸지 않습니다 — 타입으로 값을 검사할 수 없는 이유이기도 합니다(→ 13장).

      tsconfig.json — 지금 프로젝트 설정이 뜻하는 것
      {
  "compilerOptions": {
    "rootDir": "./src",      // 원본 .ts 위치
    "outDir": "./dist",      // 변환된 .js 출력 위치
    "target": "es2020",      // 어떤 JS 문법 수준으로 낮출지
    "module": "commonjs",    // 모듈 방식 (require/exports)
    "strict": true,          // ★ 엄격 모드 한 방에 켜기
    "esModuleInterop": true
  }
}
      strict: true 가 켜는 것

      strictNullChecks(null·undefined를 아무 데나 못 넣음), noImplicitAny(타입 못 정하면 암묵적 any 금지), strictFunctionTypes 등이 한꺼번에 켜집니다. 지금 노트의 규칙 대부분은 이게 켜져 있다는 전제입니다.

      모든 파일 첫 줄의 export {} 는 뭐였나

      import/export가 하나도 없는 .ts 파일은 모듈이 아니라 전역 스크립트로 취급됩니다. 그러면 ts1.ts의 add와 ts2.ts의 add가 같은 전역 공간에서 충돌해 "중복 선언" 에러가 납니다. export {} 한 줄이 그 파일을 모듈로 만들어 스코프를 분리해 줍니다. (아무것도 내보내지 않는, 순수한 선언용 한 줄입니다.)

      01

      기본 타입과 타입 추론

      원시 타입은 전부 소문자입니다. String(대문자)은 다른 것이니 쓰지 마세요. 

      const car: string = "BMW";
let age: number = 23;
let isAdult: boolean = false;
let n: null = null;
let u: undefined = undefined;

let fruits: string[] = ["사과", "바나나", "딸기"];
// fruits.push(95);   // 에러: number는 string[]에 못 들어감

      타입을 언제 쓰고 언제 생략하나

      TS는 초기값을 보고 타입을 스스로 정합니다(타입 추론). 추론이 정확하면 표기는 생략하는 게 관례입니다. 표기가 필요한 건 초기값만으로는 의도를 알 수 없을 때입니다. 

      let fruits2 = ["사과", "바나나"];   // string[] 으로 추론됨 → 표기 불필요

let userAddr;                      // 초기값 없음 → any (위험)
let score: number;                 // ← 이렇게 의도를 밝혀야 함

let mixed: (string | number)[] = ["사과", 78];  // 섞을 의도는 추론 못함 → 표기 필요

      const 와 let 은 추론 결과가 다르다 (중요)

      ts2.ts에 const userName1 = "bob"이 그냥 적혀 있었는데, 여기에 리터럴 타입 개념이 숨어 있습니다. const는 값이 바뀔 수 없으니 그 값 자체가 타입이 되고, let은 바뀔 수 있으니 넓은 타입이 됩니다. 

      const userName1 = "bob";   // 타입: "bob"   (리터럴 타입)
let   userName2 = "Tom";   // 타입: string
// userName2 = 3;          // 에러: number는 string이 아님
      여기서 리터럴 타입이 나온다

      "bob"처럼 값 하나가 곧 타입인 것을 리터럴 타입이라고 합니다. 이걸 |로 이어 붙인 게 뒤에 계속 나오는 type Filter = "all" | "active" | "completed" 같은 패턴입니다.

      헷갈리는 둘: (A|B)[] vs A[]|B[]

      ✓ (string | number)[]
      let a: (string | number)[];
a = ["사과", 1, "배"];  // OK
a.push(2);              // OK
// 요소 하나하나가 string 또는 number
      ✗ string[] | number[]
      let b: string[] | number[];
b = ["사과", "배"];     // OK (string[])
// b = ["사과", 1];     // 에러: 섞을 수 없음
// b.push(1);           // 에러: 배열 전체가
//   string[]인지 number[]인지 아직 모름
      02

      readonly 배열과 as const

      const는 변수 재할당만 막습니다. 배열 내용은 얼마든지 바꿀 수 있습니다. 내용까지 잠그려면 readonly가 필요합니다. 

      const vegetables: ReadonlyArray<string> = ["carrot", "broccoli"];
const vegetables2: readonly string[]     = ["carrot", "broccoli"]; // 위와 완전히 동일
const scores2: readonly number[]         = [100, 95, 85];

// vegetables.push("potato");  // 에러: readonly 배열엔 push가 없음
// scores2[0] = 1;             // 에러: 읽기 전용 인덱스

      그래서 바꾸는 대신 새로 만듭니다. 원본은 그대로 두고 복사본을 만드는 이 방식이 리액트 등에서 쓰는 기본 습관입니다. 

      const newArray = [...scores2, 85];   // number[] — 새 배열이라 수정 가능
console.log(newArray);               // [100, 95, 85, 85]

      as const — 전체를 통째로 얼리기

      값 뒤에 as const를 붙이면 그 안의 모든 값이 리터럴 타입 + readonly가 됩니다. 배열은 덤으로 튜플로 바뀝니다(→ 다음 장). 

      const person2 = ["Alice", 25] as const;
// 타입: readonly ["Alice", 25]
// person2[0] = "three";   // 에러: 읽기 전용

const CONFIG = { mode: "dark", retry: 3 } as const;
// 타입: { readonly mode: "dark"; readonly retry: 3 }
// as const 없으면 mode는 그냥 string으로 넓어짐
      쓰는 순간

      고정된 옵션 목록·설정 객체를 만들 때 as const를 붙이면 그 값들로 리터럴 유니온 타입을 뽑아낼 수 있습니다(→ 05장 enum 대안).

      03

      튜플 — 위치가 의미를 갖는 배열

      배열인데 길이가 고정이고 각 자리의 타입이 정해진 것. 자리마다 뜻이 다를 때 씁니다. 

      const person: [string, number] = ["Alice", 25];

console.log(person[0].toLowerCase());  // 0번은 string인 걸 아니까 문자열 메서드 OK
// console.log(person[1].toLowerCase()); // 에러: 1번은 number

person[0] = "Tiger";   // OK
person[1] = 26;        // OK
// person[1] = "26";   // 에러

      왜 굳이 튜플인가 — 반환값에서 차이가 드러난다

      ✓ 튜플 반환
      function getUserInfo(): [string, number, boolean] {
  return ["Bob", 30, true];
}
const [username, age1, isUserAdult] = getUserInfo();
// username   : string
// age1       : number
// isUserAdult: boolean
username.toUpperCase();  // OK
      ✗ 유니온 배열 반환
      function getUserInfo2(): (string | number | boolean)[] {
  return ["Bob", 30, true];
}
const [u2] = getUserInfo2();
// u2 : string | number | boolean
// u2.toUpperCase();  // 에러: 문자열인지 확신 못함
// 위치 정보가 통째로 사라졌다

      React의 const [state, setState] = useState(0)가 바로 이 튜플 구조입니다. 빈 값으로 시작할 땐 배열과 튜플의 표기를 구분해 두세요. 

      const array1: number[] = [];            // 몇 개든 상관없는 number 배열
const tuple1: [number, string] = [0, ""]; // 반드시 (number, string) 두 칸

// 추론으로 튜플 만들기
const point = [10, 20] as const;        // readonly [10, 20]
      04

      any · unknown · void · never

      네 개를 따로 외우면 계속 헷갈립니다. "값이 몇 개나 들어올 수 있나"를 축으로 한 줄에 세우면 정리됩니다.

      타입뜻대입그 값으로 할 수 있는 것
      any검사 포기아무거나아무거나 (오타도 통과 → 사실상 JS)
      unknown아직 모름아무거나좁히기 전엔 아무것도
      void반환값 없음(함수 반환 자리)반환값을 쓰지 말 것
      never값이 존재할 수 없음아무것도 불가도달 불가 표시 · 항상 throw

      any 는 왜 위험한가

      let randomValue: any = 10;
randomValue = "hello";
console.log(randomValue.length);   // 통과 (5)
randomValue = true;
console.log(randomValue.length);   // 여전히 통과! → 런타임에 undefined
randomValue.foo().bar();           // 이것도 통과 → 런타임 크래시

      unknown 은 "확인 후 사용"을 강제한다

      let unknownValue: unknown = 10;
unknownValue = "Hello";

// console.log(unknownValue.length);   // 에러: 뭔지 모르니 접근 불가

if (typeof unknownValue === "string") {
  const strLength: number = unknownValue.length;  // 여기선 string으로 좁혀짐 → OK
  console.log(strLength);
}
      한 줄 요약

      외부에서 들어와 타입을 모르는 값(API 응답, JSON.parse 결과, 라이브러리 반환)은 any 대신 unknown으로 받고, 검사한 뒤에 쓰세요. any는 에러를 없애는 게 아니라 미루는 것입니다.

      void — 반환하지 않는다는 선언

      function message(msg: string): void {
  console.log(msg);        // return 문이 없음
}

const printLength = (text: string | null): void => {
  if (text === null) {
    console.log("No text");
    return;                // 값 없는 return은 void와 모순되지 않음
  }
  console.log(`${text.length}`);
};
printLength(null);

const numbers = [1, 2, 3, 4, 5];
numbers.forEach((num): void => {   // 콜백이 값을 돌려주지 않는다는 뜻
  console.log(num);
});

      never — 실전 용도는 "빠뜨린 케이스 잡기"

      ts1.ts의 handleValue가 어렵게 느껴진 건, never를 타입이 아니라 안전장치로 쓴 코드이기 때문입니다. 유니온의 모든 갈래를 처리하고 나면 마지막 else에 남는 타입은 never입니다. 여기에 const unreachable: never = x를 두면, 나중에 유니온에 타입을 하나 추가했을 때 이 줄에서 컴파일 에러가 납니다 — 처리를 빠뜨렸다는 신호죠. 

      const handleValue = (x: string | number | boolean | object): void => {
  if (typeof x === "string") {
    // x: string
  } else if (typeof x === "number") {
    // x: number
  } else if (typeof x === "boolean") {
    // x: boolean
  } else if (typeof x === "object") {
    // x: object
  } else {
    const unreachable: never = x;   // 여기 도달 = 처리 안 한 타입이 있다
    throw new Error("Unhandled type : " + unreachable);
  }
};

handleValue("Hello");
handleValue(42);
handleValue(true);
handleValue({ name: "John" });
      이걸 exhaustiveness check 라고 부른다

      유니온 "idle" | "loading" | "success"에 "error"를 추가하는 순간, switch의 default에서 never 대입이 깨지며 "여기도 고쳐라"라고 알려줍니다. 상태 관리 코드에서 아주 자주 씁니다.

      05

      enum 과 요즘의 대안

      관련 상수들을 한 이름으로 묶는 문법입니다. 값을 생략하면 앞 값 +1로 자동 증가합니다.

      enum Color {
  Red = 1,   // 1
  Green,     // 2 (자동)
  Blue,      // 3 (자동)
}

console.log(Color.Red);        // 1
let favoriteColor: Color = Color.Blue;
console.log(favoriteColor);    // 3
      알아둘 예외

      "타입은 컴파일 후 사라진다"의 거의 유일한 예외가 enum입니다. enum은 실제 JS 객체를 만들어 냅니다. 그래서 번들 크기·트리셰이킹 문제로 실무에서는 점점 덜 씁니다.

      대안 1 — 리터럴 유니온 (가장 흔함)

      type Status = "idle" | "loading" | "success" | "error";
let currentStatus: Status;
currentStatus = "idle";
// currentStatus = "done";   // 에러 — 오타를 즉시 잡아준다

// 컴파일 결과에 아무 코드도 남지 않는다

      대안 2 — as const 객체 (값도 필요할 때)

      const Color = { Red: 1, Green: 2, Blue: 3 } as const;

type Color = typeof Color[keyof typeof Color];   // 1 | 2 | 3
const c: Color = Color.Blue;

      typeof와 keyof가 섞여 처음엔 안 읽히는 표현입니다. 지금은 "값에서 타입을 뽑는 관용구"로만 기억하고, 12장에서 두 연산자를 따로 봅시다.

      06

      type 별칭 — 타입에 이름 붙이기

      type은 새 타입을 만드는 게 아니라 이미 있는 타입에 이름을 붙이는 문법입니다. 같은 표기를 여러 곳에 반복하지 않으려고 씁니다. 

      // 반복: let userAddr: string | number; let shopAddr: string | number; ...
type Addr = string | number;
let userAddr: Addr;
let shopAddr: Addr;

      담을 수 있는 것 — 사실상 전부

      type Status  = "idle" | "loading" | "success" | "error";  // 리터럴 유니온
type Point   = { x: number; y: number };                  // 객체
type PointTuple = [number, number];                       // 튜플
type Handler = (e: MouseEvent) => void;                   // 함수

let point: Point = { x: 10, y: 20 };
const tuple2: PointTuple = [10, 20];

      & 로 합치기 (intersection)

      |가 "둘 중 하나"라면 &는 "둘 다"입니다. 기존 타입에 속성을 더할 때 씁니다.

      type Name = {
  firstName: string;
  lastName: string;
};

type Employee = Name & {
  employeeId: number;
};

let employee: Employee = {
  firstName: "John",
  lastName: "Doe",
  employeeId: 1234,      // 세 개 다 있어야 함
};
      // ts2.ts 의 예 — 두 인터페이스를 모두 만족하는 타입
interface Developer { name: string; skills: string[]; }
interface Manager   { name: string; age: number; manage(): void; }

type DevManager = Developer & Manager;

const person2: DevManager = {
  name: "Alice",
  skills: ["javascript", "typescript"],
  age: 26,
  manage(): void { console.log("do managing"); },
};
person2.manage();

      index signature — 키 이름을 미리 모를 때

      "어떤 키가 올지는 모르지만, 값은 전부 string이다"를 표현합니다. 

      type Member = {
  [key: string]: string;    // 키는 아무 문자열, 값은 반드시 string
};

let member: Member = { id: "user01", name: "alice" };
let member2: Member = { id: "user01", name: "alice", addr: "seoul" };  // 나중에 추가 OK
// let member3: Member = { id: "user01", age: 20 };  // 에러: number 값 불가
      대가

      편한 대신 오타를 못 잡습니다. member.nmae도 통과합니다(값 타입만 맞으면 되니까). 키를 알고 있다면 index signature 대신 키를 하나씩 적는 편이 훨씬 안전합니다. "키 목록은 정해져 있는데 값 타입이 같다"면 Record가 정답입니다(→ 12장).

      07

      interface — 객체의 계약서

      객체의 모양을 정의합니다. object 타입만 쓰면 왜 부족한지부터 보면 필요성이 분명해집니다. 

      let user1: object;
user1 = { name: "Alice", age: 25 };
console.log(user1);
// console.log(user1.name);   // 에러: object에는 name이 있다는 정보가 없다

interface User {
  name: string;
  age: number;
}
let user: User = { name: "David", age: 30 };
console.log(user.age);        // OK — 어떤 키가 있는지 TS가 안다

      ? — 있을 수도, 없을 수도

      interface User2 {
  name: string;
  age: number;
  gender?: string;     // 선택적 속성 → 타입은 string | undefined
}

let user2: User2 = { name: "David", age: 30 };                   // OK
let user3: User2 = { name: "David", age: 30, gender: "Male" };   // OK
user3.name = "Teddy";

// user3.gender.toUpperCase();  // 에러: undefined일 수 있음
user3.gender?.toUpperCase();    // 옵셔널 체이닝으로 안전하게

      readonly — 생성 후 못 바꾸는 속성

      interface Car {
  readonly model: string;
  year: number;
}
const car1: Car = { model: "Toyota", year: 2026 };
car1.year = 2027;          // OK
// car1.model = "hyundai"; // 에러: 읽기 전용

      인덱스 시그니처의 숨은 규칙 (여기서 막혔던 부분)

      판별 유니온 (discriminated union)

      각 인터페이스에 서로 다른 리터럴 값을 가진 공통 키(보통 type, kind)를 하나 두는 패턴입니다. 그 키만 비교하면 TS가 나머지 속성까지 전부 알아냅니다. 

      interface Car {
  type: "car";           // ← 판별 키 (리터럴 타입)
  color: string;
  start(): void;
}

interface Mobile {
  type: "mobile";        // ← 판별 키
  color: string;
  call(): void;
}

const getGift = (gift: Car | Mobile) => {
  console.log(gift.color);      // 공통 속성은 검사 없이 접근 가능

  if (gift.type === "car") {
    gift.start();               // 여기서 gift는 Car로 확정
  } else {
    gift.call();                // 여기서는 Mobile로 확정
  }
};
      원본 코드에 있던 실수

      ts2.ts에는 color: "string"이라고 따옴표가 붙어 있습니다. 이건 "문자열 타입"이 아니라 "string"이라는 글자만 허용하는 리터럴 타입입니다. color: "red"를 넣으면 에러가 납니다. 따옴표 없는 color: string이 맞습니다 — 01장의 리터럴 타입이 여기서 조용히 발목을 잡는 대표적인 경우입니다.

      단언(as)과 ! — 책임을 떠안는 문법

      as는 값을 바꾸지 않습니다. 컴파일러에게 "내가 아니까 그만 따져"라고 말하는 것뿐이고, 컴파일 후엔 흔적도 없이 사라집니다. 틀렸을 때 대신 책임져 줄 사람이 없다는 뜻입니다.

      ! (non-null assertion) — "null 아님을 보증"

      const form = document.querySelector<HTMLFormElement>("#todo-form")!;
//                                                                 ↑
// 반환 타입 HTMLFormElement | null 에서 null 을 잘라낸다

      HTML에서 id를 바꾸거나 스크립트가 <head>에서 먼저 실행되면 그 요소는 null이고, !는 그걸 막지 못한 채 다음 줄에서 "Cannot read properties of null"로 터집니다. 연습용 코드에선 편의상 쓰지만, 실제 앱에서는 아래처럼 한 번 확인하는 편이 낫습니다.

      셀프 체크

      먼저 스스로 답해 보고 펼치세요. 막히는 항목의 번호가 다시 봐야 할 장입니다.

      any와 unknown의 차이를 한 문장으로?

      둘 다 아무 값이나 받지만, any는 받은 뒤에도 아무 검사를 안 하고, unknown은 좁히기 전엔 아무것도 못 하게 막습니다. 외부에서 온 값은 unknown으로 받으세요. → 04장

      const x = "bob"과 let y = "bob"의 추론 타입은 각각?

      x는 리터럴 타입 "bob", y는 string. const는 값이 변할 수 없으니 값 자체가 타입이 됩니다. → 01장

      (string|number)[]와 string[]|number[]는 뭐가 다른가?

      앞은 요소마다 string 또는 number(섞을 수 있음), 뒤는 배열 전체가 string[] 이거나 number[](섞을 수 없고 push도 막힘). → 01장

      튜플을 쓰면 유니온 배열보다 뭐가 좋은가?

      위치별 타입이 보존됩니다. 구조분해했을 때 각 변수가 정확한 타입을 갖습니다. 유니온 배열은 전부 합집합이 되어 메서드 호출이 막힙니다. → 03장

      const unreachable: never = x;는 왜 쓰는가?

      유니온의 모든 케이스를 처리했는지 컴파일러가 검사하게 하려고요. 나중에 유니온에 타입이 추가되면 이 줄에서 에러가 나며 처리 누락을 알려줍니다. → 04장

      type과 interface 중 하나만 할 수 있는 일은?

      유니온·튜플·원시 별칭은 type만. 같은 이름으로 다시 선언해 합치는 선언 병합은 interface만. → 08장

      interface X { name: string; id: number; [key: string]: string }가 에러인 이유는?

      string 인덱스 시그니처를 선언하면 모든 문자열 키의 값이 그 타입이어야 하는데 id: number가 위반합니다. 원본 코드가 [key: number]를 쓴 이유가 이것입니다. → 07장

      제네릭이 any[]보다 나은 점은?

      입력과 출력의 타입 관계를 유지합니다. any는 정보를 버리지만 <T>(arr: T[]): T는 "number를 넣으면 number가 나온다"를 기억합니다. → 11장

      Pick과 Omit을 고르는 기준은?

      남길 게 적으면 Pick, 뺄 게 적으면 Omit. 원본에 속성이 추가될 때 Omit은 자동으로 따라오고 Pick은 그대로입니다. → 12장

      document.querySelector("#input")!.value가 에러인 이유는?

      !는 null만 제거할 뿐 타입은 여전히 Element인데, Element에는 value가 없습니다. querySelector<HTMLInputElement>("#input")처럼 요소 타입을 지정해야 합니다. → 14장

      data as T로 fetch 결과 타입을 지정하면 안전한가?

      아니요. as는 컴파일 시점의 약속일 뿐 런타임에 아무 검사도 하지 않습니다. 서버가 다른 모양을 보내도 통과합니다. → 13·14장
